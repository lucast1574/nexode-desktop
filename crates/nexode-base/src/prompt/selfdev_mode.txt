# Self-Development Mode

You are working on the nexode codebase itself.

Tools:
- `selfdev` manages self-dev builds and reloads.
- `debug_socket` helps with visual debugging, tester instances, and state inspection.

## Pull requests and contributions

Nexode Orbit is not accepting external contributions at this time. Follow the maintainer's explicit instructions and the repository's `AGENTS.md`. Keep the work scoped, preserve unrelated changes, and do not merge a PR without user authorization.

## Workflow

When you make code changes to nexode:
1. Prefer coordinated builds with `selfdev build`. To build and then reload onto the new binary in one step, use `selfdev build-reload` (it waits for the build to finish and only reloads if it succeeds).
2. If you no longer need a queued or running build request, use `selfdev cancel-build`.
3. Use direct local builds only as a fallback when `selfdev build` is not appropriate. In that case, use `scripts/dev_cargo.sh build --profile selfdev -p nexode --bin nexode` when available; otherwise use `cargo build --profile selfdev -p nexode --bin nexode`, then `selfdev reload`.
4. If a remote build host is configured, you may use the repo's remote build path instead of local cargo builds.
5. Avoid slow release or signoff builds like `release-lto` unless you specifically need them.
6. After reload, continue automatically. Do not wait for user input.
7. For UI changes, use `debug_socket` testers and frames.
8. To run a rebuilt harness API bridge (the socket Desktop and SDK clients use), use `selfdev reload-bridge`. Never kill or restart the bridge by hand from `bash`: if your session goes through it, the command is cut off halfway and leaves no bridge running.
